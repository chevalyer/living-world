# 1. Общая идея проекта

Игра представляет собой автономную 2D-симуляцию мира с видом сверху.

Мир создаётся процедурно из seed и существует независимо от игрока. В нём есть:

- рельеф;
- моря;
- реки;
- озёра;
- леса;
- поля;
- горы;
- почва;
- климат;
- погода;
- растения;
- ресурсы;
- животные в будущем;
- предметы;
- здания;
- дороги;
- поселения;
- NPC;
- социальные отношения;
- семьи;
- производство;
- экономика;
- знания;
- поколения.

Главная идея:

**игра не должна состоять из заранее написанных сценариев.**

NPC не получает команду:

«наступила зима → собери дрова».

Он видит состояние мира, своё состояние, вспоминает известную ему информацию, оценивает опасности и самостоятельно приходит к выводу, что ему следует сделать.

Мир должен позволять появляться поведению, которое разработчик напрямую не программировал.

---

# 2. Технологический стек

Основной язык проекта:

**C#**

Движок:

**Godot с поддержкой C# / .NET.**

Godot должен в основном отвечать за:

- графику;
- TileMap;
- камеру;
- UI;
- ввод;
- звук;
- отображение сущностей;
- визуальные эффекты.

Основная симуляция должна быть написана на обычном C# и по возможности минимально зависеть от Godot.

Это очень важно.

Не надо делать так, чтобы вся логика NPC находилась внутри `Node2D`, `_Process()` и сигналов Godot.

Лучше:

**Simulation Core**
→ чистый C#

**Godot Presentation**
→ отображает результаты Simulation Core.

Благодаря этому:

- симуляцию проще тестировать;
- NPC можно симулировать без рендера;
- можно ускорять время;
- можно запускать тысячи сущностей;
- меньше зависимости от SceneTree;
- проще сохранять мир;
- проще менять визуальную часть;
- архитектура не превращается в кашу.

---

# 3. Основной архитектурный подход

Основной подход:

**ECS-подобная архитектура + Data-Driven Design + модульные Systems + слабая связанность.**

Не обязательно использовать готовый ECS-фреймворк.

Можно сделать собственную систему, подходящую именно под игру.

Главный принцип:

**Entity хранит идентичность.**

**Component хранит состояние.**

**System содержит логику.**

**Definition описывает тип объекта.**

Например NPC является Entity.

Сам NPC не должен содержать огромный класс с:

- голодом;
- температурой;
- строительством;
- отношениями;
- памятью;
- движением;
- беременностью;
- торговлей.

Вместо этого у него присутствуют компоненты.

Например:

`BodyComponent`

`HealthComponent`

`InventoryComponent`

`MovementComponent`

`NeedsComponent`

`SkillsComponent`

`MemoryComponent`

`KnowledgeComponent`

`SocialComponent`

`PersonalityComponent`

`DecisionComponent`

И каждая система работает только с нужными ей компонентами.

Например `TemperatureSystem` вообще не обязан знать, что объект является человеком.

Ему достаточно:

- температуры;
- тела;
- одежды;
- окружающей среды.

Это позволяет в будущем использовать ту же систему температуры для:

- NPC;
- животных;
- еды;
- воды;
- помещений;
- костров.

---

# 4. Самое главное правило архитектуры

Новая механика не должна требовать переписывания половины проекта.

Например добавляется:

**стресс.**

Не надо менять `NPC.cs`.

Добавляются:

`StressComponent`

`StressSystem`

А другие системы могут при необходимости начать использовать стресс.

Например:

`SleepSystem`
может учитывать стресс.

`ConflictSystem`
может его увеличивать.

`DecisionSystem`
может учитывать его при принятии решений.

Если система не имеет отношения к стрессу — её код вообще не меняется.

Например:

`RiverGenerationSystem`

никак не должен знать про стресс.

# 7. Entity

Каждый существующий объект мира получает уникальный EntityId.

Например:

человек;

дерево;

куст;

камень;

предмет на земле;

топор;

здание;

дверь;

костёр.

EntityId нужен для связи систем.

Например отношения между двумя NPC должны хранить не ссылки на Godot Node, а их EntityId.

Это позволит нормально:

- сохранять мир;
- удалять сущности;
- восстанавливать связи;
- симулировать объекты без отображения.

---

# 8. Components

Компонент должен в основном содержать **данные**, а не огромную бизнес-логику.

Например `DurabilityComponent`:

текущая прочность;

максимальная прочность.

Но он не должен самостоятельно решать:

«если меня ударили топором, потерять 12 прочности».

Это задача соответствующей системы.

---

# 9. Definitions

Очень важно отделить:

**конкретный экземпляр вещи**

от

**описания типа вещи.**

Например существует definition:

**LeatherJacketDefinition**

Он описывает:

- название;
- базовый материал;
- базовую массу;
- слот одежды;
- форму;
- базовые характеристики.

А конкретная куртка NPC может иметь:

- качество 63%;
- прочность 74/100;
- влажность 30%;
- грязь;
- индивидуальный цвет;
- предыдущего владельца.

Так одна Definition может породить тысячи разных экземпляров.

---

# 10. Материалы

Материалы надо делать отдельной фундаментальной системой.

Например:

**Leather**

может иметь:

- плотность;
- гибкость;
- теплоизоляцию;
- водостойкость;
- воздухопроницаемость;
- прочность;
- горючесть;
- скорость разрушения;
- стоимость обработки.

**Iron**

имеет другие свойства.

**OakWood**

другие.

Благодаря этому вещи не являются полностью захардкоженными.

Кожаная куртка получает часть свойств от кожи.

Железная дверь — от железа.

Дубовая дверь — от дуба.

Таким образом один объект может вести себя по-разному из-за материала.

---

# 11. Одежда

Не должно существовать параметров:

`warmClothes = true`

или:

`clothingQuality = good`.

У одежды есть реальные свойства.

Например:

- слот тела;
- площадь покрытия;
- материал;
- масса;
- толщина;
- теплоизоляция;
- воздухопроницаемость;
- ветроустойчивость;
- водостойкость;
- впитывание воды;
- удобство;
- мобильность;
- защита;
- прочность;
- влажность;
- состояние;
- качество изготовления.

Слоты тела могут быть:

- голова;
- лицо;
- торс;
- внешний торс;
- ноги;
- ступни;
- руки;
- кисти.

Некоторые вещи могут занимать несколько слотов.

Температурная система анализирует весь комплект одежды.

Она не спрашивает:

«NPC тепло одет?»

Она рассчитывает реальное влияние одежды.

---

# 12. Инструменты

Аналогичный подход.

Не надо делать:

`GoodAxe`

`BadAxe`.

Топор может иметь:

- материал головки;
- материал рукояти;
- массу;
- баланс;
- остроту;
- прочность;
- качество;
- длину;
- эффективность удара.

Действие `Chop` анализирует характеристики инструмента.

Поэтому каменный и железный топор могут использовать один и тот же Action.

---

# 13. Еда

Еда тоже должна быть системой свойств.

Например ягода может иметь:

- калорийность;
- воду;
- массу;
- вкус;
- срок хранения;
- токсичность;
- питательные вещества;
- состояние;
- свежесть.

NPC не знает магический параметр:

`foodValue = 10`.

Он знает или предполагает:

«эту ягоду можно есть».

После употребления физиологические системы применяют последствия.

---

# 14. Генерация мира

World Generation должен быть полностью детерминированным.

Один и тот же seed:

→ один и тот же начальный мир.

Seed не должен использовать один огромный Random для всего проекта.

Лучше иметь отдельные deterministic random streams.

Например:

TerrainSeed;

RiverSeed;

VegetationSeed;

ResourceSeed;

NPCSeed.

Это позволяет изменить генерацию цветов и не получить совершенно другие горы.

---

# 15. Этапы генерации мира

Генерация выполняется последовательно.

Сначала формируется базовая высота.

Дальше геология.

Дальше океаны.

Дальше водосбор.

После этого реки.

Потом озёра.

Потом климат.

Потом почва.

Потом биомы.

Потом растительность.

Потом природные ресурсы.

Потом возможные стартовые NPC.

Каждый этап использует результат предыдущих.

---

# 16. Высота

Для каждой клетки мира существует значение высоты.

Это не обязательно означает настоящий 3D.

Игра остаётся 2D сверху.

Высота используется для:

- гор;
- склонов;
- рек;
- направления воды;
- температуры;
- растительности;
- движения.

---

# 17. Реки

Реки не должны рисоваться случайными линиями.

Вода должна стремиться вниз.

Система анализирует:

- высоты;
- водосбор;
- количество осадков;
- источники воды.

Маленькие потоки постепенно объединяются.

Получаются:

ручьи;

реки;

крупные реки.

Реки могут впадать:

в море;

в озеро;

в другую реку.

---

# 18. Озёра

Озеро формируется там, где вода не может продолжить двигаться вниз.

То есть озеро появляется из рельефа.

Не:

«random < 0.1 → озеро».

---

# 19. Биомы

Биом определяется не одним random.

Основные параметры:

температура;

влажность;

высота;

почва;

количество осадков;

расстояние до воды.

Например лес возникает потому, что условия подходят деревьям.

---

# 20. Растительность

Растения являются живыми сущностями симуляции.

Например дерево имеет:

- вид;
- возраст;
- размер;
- здоровье;
- воду;
- стадию роста;
- количество древесины;
- сезонность.

Куст может:

- расти;
- производить ягоды;
- терять ягоды;
- погибать;
- размножаться.

---

# 21. Растения не должны знать дату

Например растение не должно иметь:

«если сейчас декабрь → перестать расти».

Растение реагирует на:

- температуру;
- солнечный свет;
- влагу;
- состояние почвы.

Зимой изменяются именно эти параметры.

В результате растение естественно замедляет рост.

---

# 22. Время мира

Есть полноценный календарь.

Например:

18 октября 1372 года.

Время включает:

- секунды;
- минуты;
- часы;
- дни;
- месяцы;
- годы.

Все системы получают время через единый `SimulationClock`.

Нельзя позволять разным системам самостоятельно считать дни.

---

# 23. Simulation Tick

Симуляция должна работать через фиксированный tick.

Например:

один simulation tick = определённый кусок игрового времени.

Не вся логика обязана обновляться каждый кадр.

Например:

Movement может обновляться часто.

Погода — реже.

Рост дерева — ещё реже.

Отношения вообще только при событиях.

Это резко повышает производительность.

---

# 24. Сезоны

Сезоны являются следствием календаря и климатической модели.

SeasonSystem определяет общую фазу года.

Но сам сезон не должен напрямую командовать всеми системами.

Зима влияет на:

температуру;

длину дня;

осадки;

солнце.

И уже остальные системы реагируют на эти изменения.

---

# 25. Вода и лёд

Вода имеет температуру.

Если условия достаточно холодные достаточно долго:

вода постепенно замерзает.

Не обязательно сразу вся клетка.

Можно учитывать толщину льда.

В будущем это позволит:

NPC ходить по льду;

тонкому льду ломаться;

льду таять весной.

---

# 26. Погода

Погода должна хранить:

температуру;

осадки;

ветер;

облачность;

влажность.

Она зависит от:

сезона;

местного климата;

высоты;

водоёмов.

---

# 27. Чанки

Мир желательно разделить на чанки.

Например участок карты делится на небольшие области.

Это нужно для:

- генерации;
- сохранения;
- навигации;
- обновлений;
- производительности;
- отображения.

Далёкие чанки необязательно симулировать с той же точностью, что и область рядом с камерой.

Но результат их симуляции не должен становиться нелогичным.

---

# 28. NPC

NPC — полноценная Entity.

Он не должен быть классом, содержащим весь код человека.

NPC собирается из компонентов.

Примерные группы:

Identity;

Body;

Needs;

Inventory;

Equipment;

Skills;

Traits;

Personality;

Memory;

Knowledge;

Relationships;

Movement;

Decision;

LifeStage;

Health.

---

# 29. Генерация NPC

При создании NPC генерируются:

- имя;
- фамилия;
- пол;
- дата рождения;
- возраст;
- базовая внешность;
- физические характеристики;
- характер;
- склонности;
- стартовые навыки;
- некоторые предпочтения.

Генерация имени должна находиться отдельно.

`NameGenerator`

не должен знать ничего о:

голоде;

семьях;

строительстве;

AI.

Можно иметь отдельные наборы имён.

При необходимости исключается буква `ё`.

---

# 30. Возраст

Возраст считается из даты рождения.

Не хранить одновременно:

`Age = 34`

и отдельную дату рождения, если возраст можно вычислить.

Дата рождения является источником истины.

---

# 31. Стадии жизни

Можно использовать стадии:

младенец;

ребёнок;

подросток;

взрослый;

пожилой.

Но стадия не должна магически задавать всё поведение.

Она влияет на:

- физические возможности;
- скорость обучения;
- доступные действия;
- потребности;
- социальные ограничения.

---

# 32. Физиология

Человек имеет физическое состояние.

Минимально:

- здоровье;
- энергия;
- гидратация;
- температура тела;
- сон;
- усталость;
- голод.

Позже:

- боль;
- кровь;
- болезни;
- раны;
- стресс.

---

# 33. Потребности

Потребность не должна сразу создавать действие.

Например:

голод повышается.

Система просто сообщает:

организму требуется энергия.

А Decision System уже решает, насколько это важно по сравнению с другими проблемами.

---

# 34. Температура тела

Температура NPC рассчитывается из:

температуры воздуха;

ветра;

влажности;

одежды;

физической активности;

помещения;

близости к огню;

состояния одежды.

NPC может:

замерзать;

перегреваться.

---

# 35. Skills

Навыки должны быть независимыми.

Например:

Mining;

Woodworking;

Farming;

Building;

Cooking;

Medicine;

Social;

Tailoring.

Но сама система навыков не должна знать, зачем навык нужен.

Она только:

хранит опыт;

вычисляет уровень;

принимает опыт.

---

# 36. Получение опыта

Action может сообщить:

NPC успешно выполнил определённую деятельность.

SkillSystem начисляет соответствующий опыт.

Например строительство стены развивает Building.

---

# 37. Характер

Черты характера не должны полностью заменять AI.

Они изменяют **оценку вариантов**.

Например:

жадный NPC сильнее ценит собственные ресурсы.

общительный сильнее ценит взаимодействие.

осторожный сильнее учитывает риски.

агрессивный легче выбирает конфликт.

Но базовая система решений остаётся общей.

---

# 38. Знания NPC

Нужно строго разделять:

**истину мира**

и

**то, что знает NPC.**

World знает:

на координате существует яблоня.

NPC может этого не знать.

NPC должен узнать об объекте через:

наблюдение;

разговор;

обучение;

память.

---

# 39. Perception

PerceptionSystem определяет, что NPC прямо сейчас способен воспринимать.

Например:

вижу дерево;

слышу человека;

ощущаю холод;

вижу огонь;

чувствую дождь.

В будущем можно учитывать:

радиус зрения;

препятствия;

освещение.

---

# 40. Memory

NPC сохраняет важные наблюдения.

Например:

«на востоке есть куст ягод».

Но это не истина.

Это память.

Через несколько дней ягоды могли исчезнуть.

NPC может прийти туда и обнаружить, что информация устарела.

---

# 41. Knowledge

Knowledge — более общее понимание мира.

Например NPC знает:

дерево горит;

еда уменьшает голод;

огонь согревает;

железо можно обрабатывать;

зимой обычно холоднее.

Knowledge отличается от Memory.

Memory:

«там находится конкретное дерево».

Knowledge:

«деревья дают древесину».

---

# 42. Обучение

NPC может получать знания:

самостоятельным опытом;

наблюдением;

от другого NPC.

Например опытный кузнец может обучать другого.

Но это не:

`student.Mining += 10`.

Teaching System учитывает:

- навык учителя;
- навык ученика;
- длительность;
- внимание;
- отношения;
- сложность темы.

---

# 43. Decision System

Это одна из центральных частей игры.

У NPC не должно быть списка:

`FindFoodGoal`

`PrepareWinterGoal`

`BuildHouseGoal`

которые запускаются по условиям.

Вместо этого есть:

**Situation Evaluation.**

Она анализирует текущее состояние NPC.

Например:

температура тела падает;

голод небольшой;

ночь приближается;

NPC устал.

Каждой проблеме вычисляется важность.

---

# 44. Dynamic Desired State

После анализа создаётся временное желаемое состояние.

Например:

`bodyTemperature > safeMinimum`

Это не заранее написанная сюжетная цель.

Она появилась потому, что текущее состояние опасно.

После достижения нужной температуры эта цель исчезает.

---

# 45. Action System

Все действия должны быть максимально универсальными и атомарными.

Например:

Move;

PickUp;

Drop;

Eat;

Drink;

Wear;

Remove;

Sleep;

Chop;

Mine;

Dig;

Cut;

Build;

Repair;

Give;

Trade;

Talk;

Teach;

Take;

Craft.

---

# 46. Action не знает зачем его выполняют

`ChopAction`

не знает:

NPC хочет построить дом.

Он знает только:

можно ли рубить;

какой инструмент нужен;

сколько времени займёт;

сколько энергии потребуется;

что произойдёт с деревом;

какие ресурсы появятся.

---

# 47. Preconditions

У каждого Action есть условия выполнения.

Например Build может требовать:

- способность двигаться;
- материалы;
- подходящее место;
- физическую возможность;
- нужный инструмент.

Важно:

не проверять конкретного NPC.

Система проверяет компоненты и свойства.

---

# 48. Effects

Action должен описывать потенциальный эффект.

Например:

Eat:

уменьшает количество еды;

увеличивает энергию;

увеличивает воду в организме;

может вызвать отравление.

Благодаря effects Decision System способен понимать, какие действия способны решить проблему.

---

# 49. Планирование

NPC может искать цепочку действий.

Например он замерзает.

Желаемое состояние:

температура тела выше.

Возможный вариант:

подойти к костру.

Если костра нет:

разжечь костёр.

Но нет древесины:

найти дерево;

срубить дерево;

поднять древесину;

вернуться;

разжечь костёр.

Это появляется из возможностей действий.

Не существует отдельного сценария:

`GetWarmScript`.

---

# 50. Utility

Разные решения получают utility score.

Учитываются:

- насколько сильно действие решает проблему;
- сколько времени требует;
- расстояние;
- риск;
- стоимость;
- навыки;
- характер;
- отношения;
- ресурсы.

NPC выбирает не всегда самый прямой вариант.

---

# 51. Пример холода

NPC замерзает.

Варианты:

зайти домой;

надеть куртку;

развести костёр;

попроситься в чужой дом;

пойти к существующему огню.

DecisionSystem сравнивает варианты.

Если куртка находится в инвентаре:

надеть её очень дёшево.

Если дом в двух шагах:

зайти туда тоже разумно.

Если ближайшее дерево далеко:

строить костёр может быть хуже.

---

# 52. Новые предметы автоматически входят в существующую систему

Допустим позже разработчик добавляет:

**шерстяной плащ.**

Если плащ имеет:

Wearable;

Insulation;

Material;

NPC AI не требуется переписывать.

Температурная система автоматически учтёт вещь.

DecisionSystem увидит, что её использование улучшает состояние NPC.

---

# 53. Социальная система

Отношение между NPC — отдельная сущность данных.

Не просто:

`friend = true`.

Для пары NPC можно хранить:

- знакомство;
- доверие;
- симпатию;
- уважение;
- привязанность;
- раздражение;
- страх;
- романтический интерес;
- долговые обязательства.

---

# 54. Relationships не должны быть симметричными

NPC A может доверять NPC B.

NPC B может не доверять NPC A.

Это нормально.

Каждое направление отношений хранится отдельно.

---

# 55. Социальные события

Например NPC A дал еду NPC B.

Это создаёт SocialEvent.

RelationshipSystem анализирует событие.

В зависимости от характера и контекста:

может повыситься доверие;

симпатия;

благодарность.

---

# 56. Ссоры

Конфликт не должен происходить:

«каждые 5 минут random chance».

Причина должна появляться из ситуации.

Например:

- спор за ресурс;
- отказ помочь;
- нарушенное обещание;
- несправедливый обмен;
- агрессивное поведение;
- разные интересы.

Характер влияет на реакцию.

---

# 57. Подарки

GiftAction позволяет передать предмет.

NPC сам решает:

готов ли он отдавать вещь.

На решение влияют:

- личная нужда;
- ценность предмета;
- отношения;
- количество запасов;
- характер.

Другу он может отдать вещь бесплатно.

---

# 58. Торговля

Цена не обязана быть глобальной.

Каждый NPC может оценивать вещь индивидуально.

Для голодного человека еда намного ценнее.

Для человека с огромным запасом еды — меньше.

Обмен становится результатом двух оценок.

---

# 59. Партнёрство и семья

Романтическое партнёрство формируется через социальную систему.

Условия могут учитывать:

- допустимый взрослый возраст;
- взаимный интерес;
- отношения;
- совместимость;
- отсутствие конфликтующих отношений.

Никаких автоматических пар по random.

---

# 60. Дети

Если два взрослых совместимых партнёра принимают соответствующее решение, FamilySystem может инициировать беременность у NPC женского пола.

Беременность существует как состояние организма.

Она имеет продолжительность.

После завершения создаётся новая NPC Entity.

---

# 61. Наследование

Ребёнок может получать часть характеристик родителей.

Например:

- некоторые особенности внешности;
- диапазоны физических параметров;
- определённые склонности.

При этом добавляется случайная вариативность.

Характер не должен полностью копироваться.

---

# 62. Детство

Ребёнок не является взрослым NPC с уменьшенными характеристиками.

У него ограничены доступные Actions.

Он может:

- двигаться;
- играть;
- наблюдать;
- разговаривать;
- исследовать;
- учиться;
- помогать в простых вещах.

Но не выполняет полноценную тяжёлую работу.

---

# 63. Родители

Родительство тоже не должно быть жёстким сценарием.

Ребёнок имеет потребности.

Родитель знает:

ребёнку нужна еда.

Социальные связи и привязанность увеличивают utility помощи ребёнку.

---

# 64. Передача знаний поколениям

Это очень важная часть мира.

NPC может умереть.

Если он никому не передал знание — оно может исчезнуть.

Если обучил детей и других жителей — знание сохраняется.

Так со временем может появляться культура поселения.

---

# 65. Строительство

Здание не должно быть одной Entity:

`House`.

Дом желательно представлять как набор элементов:

- стены;
- двери;
- пол;
- крыша;
- мебель.

RoomSystem анализирует замкнутые пространства.

---

# 66. Помещения

Если стены и крыша образуют помещение:

создаётся понятие Room.

Room влияет на:

- ветер;
- температуру;
- дождь;
- безопасность.

Тогда NPC может сам понимать, что помещение помогает от холода.

---

# 67. Строительные материалы

Стена из дерева и стена из камня используют одну механику стены.

Но имеют разные свойства:

прочность;

изоляцию;

горючесть;

массу.

---

# 68. Пути и дороги

NPC постоянно перемещаются по миру.

Каждая клетка может хранить `TrafficValue`.

Когда NPC проходит:

TrafficValue немного увеличивается.

Со временем растительность вытаптывается.

Получается тропа.

Если путь активно используется:

тропа может становиться более выраженной.

NPC предпочитают удобные пути.

Из-за этого появляется feedback loop:

по дороге ходят чаще;

она становится лучше;

поэтому по ней начинают ходить ещё чаще.

---

# 69. Навигация

Pathfinding учитывает стоимость клетки.

Например:

трава = обычная стоимость;

грязь = выше;

глубокий снег = ещё выше;

дорога = ниже.

Таким образом инфраструктура реально полезна.

---

# 70. Поселения

Не надо сразу создавать `VillageAI`.

Сначала должны нормально работать отдельные NPC.

Поселение постепенно возникает из:

общего жилья;

ресурсов;

социальных связей;

частых маршрутов;

совместной работы.

---

# 71. Коллективные потребности

Позже можно добавить слой анализа состояния сообщества.

Например жители замечают:

еды мало;

жилых мест мало;

водоисточник далеко.

Но решения всё равно выполняют отдельные NPC.

---

# 72. Профессии

Профессия не должна полностью управлять человеком.

Лучше считать её специализацией.

Например NPC часто занимается строительством.

Его Building Skill растёт.

Общество начинает понимать:

он хорош в строительстве.

Он чаще получает соответствующие задачи.

В результате естественно возникает Builder.

---

# 73. Crafting

Предметы лучше создавать через операции, а не только через рецепты уровня:

3 wood + 2 stone = axe.

Можно иметь:

обработку материала;

резку;

соединение;

нагрев;

ковку;

шитьё.

Это позволит потом создавать более глубокую производственную систему.

---

# 74. Ресурсы

Ресурс должен существовать физически.

Например дерево после рубки не превращается напрямую в:

`+5 Wood` в глобальной переменной.

Создаются реальные предметы древесины.

Их нужно:

поднять;

перенести;

хранить;

использовать.

---

# 75. Инвентарь

Инвентарь должен учитывать хотя бы:

- массу;
- вместимость;
- предметы.

В будущем:

- объём;
- контейнеры;
- карманы;
- сумки.

---

# 76. Складирование

Предметы должны иметь владельца или место хранения.

NPC может знать:

в складе находится еда.

Но опять же это Knowledge.

Если кто-то вынес еду, информация может устареть.

---

# 77. Ownership

Нужно отделить:

`кто физически держит предмет`

и:

`кому предмет принадлежит`.

Украденная вещь может физически находиться у другого NPC, но SocialSystem знает владельца.

Это понадобится для конфликтов.

---

# 78. Events

Системы не должны напрямую жёстко вызывать друг друга везде.

Полезно иметь EventBus.

Например:

NPC получил урон.

Создаётся событие.

HealthSystem обработал урон.

SocialSystem может увидеть:

кто его причинил.

MemorySystem может запомнить.

RelationshipSystem уменьшит доверие.

Но DamageSystem не должен сам лазить во все эти системы.

---

# 79. Команды и события

Полезно разделить:

**Command**

«попробовать что-то сделать».

и:

**Event**

«что-то уже произошло».

Например:

`GiveItemCommand`

после успешного выполнения:

`ItemGivenEvent`.

Это резко уменьшает связанность.

---

# 80. Simulation Pipeline

Порядок обновления систем должен быть определён явно.

Например условно:

время;

окружение;

погода;

физиология;

восприятие;

память;

оценка ситуации;

планирование;

actions;

движение;

результаты действий;

социальные последствия.

Не надо надеяться на случайный порядок `_Process()`.

---

# 81. Детерминированность

При одинаковом:

seed;

начальном состоянии;

последовательности действий;

результат симуляции желательно делать одинаковым.

Это очень помогает искать баги.

Если произошёл странный баг на году 1384, можно попытаться повторить симуляцию.

---

# 82. Random Service

Нельзя разбрасывать по проекту:

`new Random()`.

Должен существовать централизованный deterministic random service.

Разные системы получают свои потоки random.

---

# 83. Save System

Сохранение должно сохранять не Godot-сцену, а состояние симуляции.

Например:

World Seed;

World Time;

Chunks;

Entities;

Components;

Relationships;

Memory;

Knowledge;

Items;

Buildings.

---

# 84. Versioning сохранений

Формат сохранения должен иметь версию.

Потому что проект будет постоянно меняться.

Например позже добавится StressComponent.

Старый save должен либо автоматически мигрироваться, либо корректно загрузиться со значениями по умолчанию.

---

# 85. Presentation Layer

Godot не является источником истины.

Например NPC визуально отображается через `NpcView`.

Он получает данные Simulation Entity.

Если View удалился из-за того, что NPC далеко от камеры:

сама NPC Entity продолжает существовать.

---

# 86. Не создавать Node на всё

Очень важно.

Если на карте:

30 000 деревьев;

5 000 кустов;

100 000 предметов;

не надо создавать 135 000 тяжёлых Godot Node.

Simulation хранит их как лёгкие данные.

Godot отображает только нужные объекты.

---

# 87. Level of Simulation

Объекты рядом с игроком можно симулировать подробно.

Далеко — реже.

Например NPC рядом:

полный pathfinding и действия.

NPC далеко:

более крупный шаг симуляции.

Но логика должна оставаться совместимой.

---

# 88. Debug Tools

Для такого проекта debugging обязателен.

Нужен специальный режим разработчика.

При выборе NPC должно быть видно:

имя;

возраст;

здоровье;

температуру;

потребности;

инвентарь;

одежду;

навыки;

отношения;

что он сейчас воспринимает;

что помнит;

что сейчас считает главной проблемой;

какие варианты действий рассматривает;

почему выбрал именно текущее действие.

Без этого AI невозможно будет нормально отлаживать.

---

# 89. Decision Debugger

Особенно нужен лог решений.

Например:

NPC freezing risk: 0.82

варианты:

Wear Jacket: 0.91

Enter House: 0.77

Light Fire: 0.43

Eat Berry: 0.02

выбрано:

Wear Jacket.

Тогда будет понятно, почему NPC сделал именно это.

---

# 90. Performance Profiling

Каждая система должна уметь показывать:

время выполнения;

число обработанных сущностей.

Особенно:

Pathfinding;

DecisionSystem;

WorldGeneration;

PlantSimulation;

Perception.

---

# 91. Tests

Simulation Core должен покрываться тестами.

Например:

вода течёт вниз;

NPC не может съесть отсутствующую еду;

мокрая одежда меняет теплоизоляцию;

предмет ломается;

растение не растёт при слишком низкой температуре;

Relationship обновляется после события;

ребёнок не может выполнять взрослое действие.

---

# 92. Не тестировать только игру вручную

Если для проверки каждой механики надо запускать Godot и ждать две минуты — разработка быстро станет адом.

Чистая C# симуляция позволяет запускать тысячи тестов автоматически.

---

# 93. Правило ответственности файлов

Каждый файл должен отвечать за понятную вещь.

Но не надо доводить это до абсурда.

Не обязательно делать отдельный класс на:

`RedFlower`

`BlueFlower`

если они работают одинаково.

Тогда используется один PlantSystem и разные PlantDefinition.

Правило:

**разные данные → Definition.**

**разная логика → отдельный класс/System.**

---

# 94. Никаких глобальных if по конкретным предметам

Очень плохой вариант:

если предмет LeatherJacket → +20 тепла.

если предмет WoolCoat → +40.

Правильно:

TemperatureSystem читает свойства InsulationComponent.

---

# 95. Никаких глобальных if по профессиям

Плохо:

если Profession == Builder → может строить.

Лучше:

Action проверяет нужные свойства и навыки.

Профессия только помогает AI предпочитать знакомую деятельность.

---

# 96. Никакого магического знания AI

DecisionSystem не должен иметь прямой доступ к:

`World.FindNearestFood()`.

Если NPC не знает, где еда, он не должен magically идти туда.

Он может:

искать;

исследовать;

спросить;

вспомнить.

---

# 97. Не делать AI всезнающим

Это один из самых важных моментов всей игры.

Интересное поведение появляется именно из несовершенной информации.

Один NPC знает расположение железа.

Другой нет.

Первый может рассказать второму.

# 104. Финальный принцип проекта

Весь проект должен строиться вокруг идеи:

**объекты описывают, чем они являются.**

**системы определяют, как работает мир.**

**NPC воспринимают только часть этого мира.**

**NPC оценивают своё состояние и известную им обстановку.**

**NPC самостоятельно выбирают действия, способные изменить ситуацию.**

Именно это должно быть фундаментом проекта на **Godot + C#**.

Godot отвечает в основном за отображение игры.

C# Simulation Core отвечает за сам мир.

Если этот фундамент сделать нормально, потом можно годами добавлять:

животных;

болезни;

войны;

религии;

экономику;

технологии;

политику;

наследование;

пожары;

эпидемии;

миграцию;

преступность;

культуру;

земледелие;

торговлю между поселениями;

не ломая весь существующий проект.

Главная цель архитектуры:

**не написать игру с тысячей правил.**

А создать набор универсальных правил, из взаимодействия которых самостоятельно появляется сложный живой мир.
